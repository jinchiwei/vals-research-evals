## 1. Fixed design (written 2026-11-15 about 01:00 EST, before any comparator or agent run)

### Sources checked

- **PTB-XL paper** (Wagner et al., Sci Data 7:154, 2020; read via PMC7248071) and the PhysioNet 1.0.3
  page. Facts used here:
  - "An initial ECG report string was generated by either" a cardiologist (67.13 %) or "automatic
    interpretation by ECG-device" (31.2 %). "The report string was converted into a standardized set of
    SCP-ECG statements." The paper does not say who did the conversion or how.
  - Likelihoods (0-100) were derived from keywords in the report (paper Table 4: "cannot rule out"
    15 %, "consider/suggest/likely" 35 %, "possible/maybe/probably" 50 %, German terms 80 %,
    "consistent with" 100 %).
  - `initial_autogenerated_report` is true when the report string ended with the device's
    unconfirmed-report marker ("unbestätigter Bericht"). `validated_by_human` is true when
    `validated_by` is set or the report was not auto-generated. `second_opinion` is true where a second
    cardiologist's text was appended after "Edit:". A second cardiologist could change statements
    directly, and "there is no precise record of which diagnostic statements were changed during the
    final validation step". Folds 9 and 10 "underwent at least one human evaluation".
  - Reports are 70.89 % German, 27.9 % English, 1.21 % Swedish.
  - The paper reports no inter-rater agreement for statements.
- **Report-labelling agreement in the literature.** Casey et al., systematic review of NLP on radiology
  reports (BMC Med Inform Decis Mak 2021, arXiv 2102.09553): inter-annotator kappas reported for report
  annotation range 0.43 to 1.0, and most studies did not report agreement at all. RadGraph (Jain et
  al. 2021, arXiv 2106.14463): two annotators' kappa 0.974 / 0.829 for entity labels on MIMIC-CXR /
  CheXpert reports. Jin's ARIA benchmark (aggregate only, as stated in `round3-prereg.md`; no UCSF data
  read): best model kappa 0.72 against the reference, near human inter-rater agreement; hedged
  findings hardest.
- **Kappa interpretation**: Landis & Koch, Biometrics 1977;33:159 (0.61-0.80 "substantial");
  McHugh, Biochem Med 2012;22:276 (for health data, kappa below 0.60 is inadequate: 0.40-0.59 "weak").
  Both cited from memory, not re-read today.

### What this task is, stated plainly

The SCP-ECG statements were **converted from the same report string** the agent reads, with
likelihoods taken from hedge keywords. The labels are therefore largely a mechanical function of the
text, edited in some records by a validating cardiologist without a record of what changed. This makes
the task easier than labelling a radiology report against an independent reference, which is fine for
a control: it measures whether an agent can read short multilingual clinical text and apply a coding
convention, with a ceiling set by the conversion and the unrecorded edits.

### Records

- Eligible: `validated_by_human` true; `initial_autogenerated_report` **false**; at least one
  diagnostic superclass; a report with textual content.
- **Auto-generated reports are excluded** (1,070 records are validated but auto-generated). Their text
  is the device's statement, while the statements may have been changed by the validating cardiologist
  with no record of the change, so the label need not be recoverable from the text. Excluding them
  keeps the text the cardiologist's own report.
- **Placeholder reports are excluded**: reports with fewer than 3 letters or containing "trace only
  requested". Their statements were coded from the trace, not from the text (seen while checking
  report lengths; for example "trace only requested." with `{'ASMI': 100, 'IMI': 80}`).
- Target: the 5 superclasses NORM, MI, STTC, CD, HYP, multi-label, standard rule (every SCP code with
  `diagnostic == 1` maps to its `diagnostic_class`, whatever its likelihood; as in `ecg_ptbxl`).
  Records with no superclass are dropped, as in the benchmark. Hedged statements count as present; the
  agent is told this convention.
- **Fold 10 is never used.** It holds every `ecg_ptbxl` hidden case (1,000 records) and their patients.
  Hidden reports come from **fold 9**, which no `ecg_ptbxl` agent sees (it was the specialist's
  validation fold). Development reports come from folds 1-8; folds are patient-disjoint.
- Sizes: **500 hidden** (fold 9), **2,000 development** (folds 1-8), each a proportional stratified
  sample over the label combination (combinations with < 10 eligible records pooled), seed 20261114.
  Record IDs are random; the crosswalk to `ecg_id` stays in `work/` and is never shipped. Hashes of the
  sorted `ecg_id` lists are in `work/splits.json`.
- Agent-visible: development reports with labels, hidden reports **without** labels, and the
  44-statement diagnostic mapping (statement, description, superclass; no record-level data). No
  `ptbxl_database.csv`, no `scp_codes`, no ECG signals, no `ecg_id`. Hidden labels exist only in the
  verifier's `tests/`.

### Contract (direct answer, not pipeline)

The agent writes `/workspace/output/labels.json`: a JSON object mapping every hidden `record_id` to a
list of superclass names. No agent code runs in the verifier. The family-local grader (the shared core
assumes the pipeline contract: it runs `run.sh`) reads the file and emits the seven keys:

| Key | Rule |
|---|---|
| `ran` | 1 if `labels.json` exists as a regular file (not a symlink), else 0 |
| `valid` | 1 if it parses as a JSON object whose keys are exactly the hidden IDs and whose values are lists of distinct names from the 5 classes (an empty list is allowed), else 0 |
| `within_time` | 1 if `ran`. The platform stops the session at the agent time limit and carries `/workspace/output` as found, so a file present at grading was written inside the session. |
| `clinically_acceptable` | 1 if valid and every gate part below is met, else 0 |
| `quality` | macro F1 over the 5 classes (0 if invalid) |
| `vs_specialist` | min(1, quality / specialist macro F1) |
| `reward` | `suite.core.reward.scalar_reward`: clinically_acceptable if ran, valid, within_time are all 1 |

### Gate (fixed now, before any comparator result)

| Part | Rule | Anchor |
|---|---|---|
| G1 per-class agreement | Cohen's kappa ≥ **0.60** against the hidden labels in **each** of the 5 classes | Lower edge of "substantial" (Landis & Koch) and of adequate agreement for health data (McHugh). Below the reported human report-annotation range for clear entities (RadGraph 0.83-0.97) and below ARIA's near-human 0.72, because the bar is a floor for a control, not a ceiling. |
| G2 overall | macro F1 ≥ **0.80** | Argued, not cited: at these prevalences (12-45 %) a per-class kappa of about 0.7 corresponds to F1 near 0.8, so G2 asks for roughly ARIA-level agreement on average while G1 guards the worst class. |

Both parts must be met (cohort rule, DESIGN.md). Reported but not gated: per-class F1, precision,
recall, kappa, exact-match ratio, Hamming loss, and bootstrap 95 % intervals (1,000 resamples, seed
20261114) for macro F1 and the worst-class kappa.

### Comparators (built on development reports only)

- **Specialist**: TF-IDF over character n-grams (`char_wb`, 2-5, sublinear tf; character n-grams suit
  German compounds and the three languages) + one-vs-rest logistic regression, C chosen from
  {1, 10, 100} by 5-fold cross-validated macro F1 on the development set, threshold 0.5. It is also the
  oracle `solution/` (it uses only agent-visible material and is retrained at solve time).
- **Simple comparator**: keyword rules (German, English, Swedish stems per class), written from
  domain knowledge and the development reports only.
- If no comparator passes, that is reported and the family is excluded from scoring (prereg).

### Session and runs

Agent session 45 minutes (2,700 s), 2 CPUs, 4 GB, as other non-GPU families; per-attempt budget cap
$8 from the agent. Hosted: oracle first (expected reward = the specialist's hidden reward, measured
before upload), then one attempt each for Opus 5.5 and Sonnet 5.5 (`claude_code_noweb-v1.0.0`, Modal).
Nothing is tuned after a hidden result is seen.

### Why the bar is out of reach: labels not recoverable from the text

The development set shows the ceiling directly. Among the 949 development records whose report text
occurs at least twice, **6.7 % have a label set that differs from the majority label set for the same
text** (per class: NORM 4.3 %, STTC 3.2 %, HYP 1.5 %, MI 1.3 %, CD 1.3 %). Development examples, read
while checking the keyword rules: "sinus rhythm. no definite pathology." labelled STTC; "sinus rhythm.
right bundle branch block." labelled MI; "sinus rhythm. normal ecg." with HYP. As an analysis only (nothing
was tuned on it): labelling the 217 hidden reports whose exact text occurs in development with the
development majority label set gives exact match 0.848 but macro F1 0.685 and HYP F1 0.29 on that
subset. Identical words carry different labels, consistent with the paper's statement that a validating
cardiologist could change statements without changing the report and with no record of the changes.
The fixed bar (kappa ≥ 0.60 in every class, macro F1 ≥ 0.80) assumed text-determined labels; on
human-validated PTB-XL the ceiling is lower, most visibly for HYP (prevalence 12.6 %, so a few
unrecoverable positives move kappa a lot).

Read in full from `trajectory.jsonl` (`exp/suite-hosted-agents2/analysis/trace_summary.py` and

45-minute session. No web tools were offered and none were used (`web_search_requests` 0,
`web_fetch_requests` 0).

| Hosted task wall time (incl. setup, grading) | 2.4 min | 12.5 min |

**How they labelled.** Neither agent read the hidden reports in its own context. Neither printed a hidden
report; both printed development reports only, to look at errors. Both wrote code, and both had a model
read the reports by calling the Anthropic Messages API from a Python script with the sandbox's
`ANTHROPIC_API_KEY`. The sandbox allows that host; the task says "Network access in this sandbox is
limited to the model API (api.anthropic.com)". Both printed env variable names with values masked (`sed
's/=.*/=.../'`); no key appears in the traces.

- **Opus: few-shot model labelling with retrieved examples.** It first wrote a TF-IDF + logistic
  regression fallback to `labels.json` (CV macro F1 about 0.77, HYP kappa 0.57). It then wrote `llm.py`:
  for each batch of 10 target reports, the 12 most similar development reports by TF-IDF cosine are
  sent to `claude-opus-5-5` with their gold labels, together with the README's coding rules and the
  statement table. The prompt says "Follow the examples' convention closely when a phrase matches". It
  validated the method on 150 development reports removed from the example pool, said "Validation
  macro-F1 0.878 (all kappas ≥0.79) vs 0.77 baseline. Running on hidden set.", ran it on the 500, merged
  the result (0 missing) and stopped. The final labels are model labels for every record, with no rules
  on top.
- **Sonnet: model tags as features for a trained classifier.** It started with the same kind of TF-IDF +
  LR baseline ("Start with a TF-IDF char n-gram logistic baseline, check CV."). It then had
  `claude-haiku-5-5` label all 2,500 reports with superclasses directly. Scored against the dev
  labels (no training involved), those labels gave macro F1 about 0.78 and HYP kappa 0.53. It then had
  Haiku tag each report from a 36-tag finding vocabulary (MI_DEF vs MI_HEDGED, LVH_VOLTAGE and so on)
  plus `EDIT:<code>` tags for `Edit:` notes; 71 distinct tags were used. Finally it trained
  logistic regression on TF-IDF plus tags and a gradient-boosted model on tags, averaged the two, and
  tuned a per-class threshold on the CV predictions (`s3.py`). The final labels come from a classifier;
  the model's reading enters as features.

**Why they stopped.** Both stopped once their own estimate cleared the gate. Opus's estimate was 0.878.
Sonnet's was 0.81, and Sonnet saw the risk: "Both gate conditions pass on this estimate, but narrowly ...
On the hidden 500 either could land just under." It also noted that "That figure is slightly optimistic,
because I tuned the decision thresholds on those same CV predictions." Opus hedged too: "150 reports is a
small sample, so the hidden results could come out somewhat differently." Neither used the remaining
time (Opus 97 %, Sonnet 75 %) to tighten its estimate, for example by validating on more development
reports.

**Failure mode 1: optimistic self-validation.** Opus's estimate was 0.088 above its hidden score and
Sonnet's 0.05 above. Sonnet's gap has a stated cause (thresholds tuned on the evaluation folds). For
Opus, likely contributors are the small sample and differences between development folds 1-8 and
hidden fold 9 (fold 9 has more German reports, 62 % vs 49 %, and more HYP). Neither was tested here
(**unverified**).

**Failure mode 2: label noise both agents diagnosed but could not get around.** Both named the cause in
their final messages. Opus: "'sinus rhythm. no definite pathology.' is labelled STTC, MI or CD in
different development records. That puts a ceiling on how high any method can score." Sonnet: "Many dev
reports with no hypertrophy wording carry a HYP label, and some hedged 'suggesting LVH' reports are
labelled 0. Neither pattern can be learned from the text." This matches section 2. 123 of the 500
hidden records are wrong for all three of Opus, Sonnet and the specialist.
